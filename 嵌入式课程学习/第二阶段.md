- memory_map 函数简单理解 f(va,pid) = pa

- 为什么有线程，进程间上下文切换时，系统开销比较大（每个进程都需要分配内存映射表）
	- 一个进程中使用多个调度体（线程）共用一张内存映射表
- **与进程的区别【面试常问】**
	- 共性：都是任务的调度体，具有任务的调度能力。 多任务 —— 多个代码段（函数集）
	- 区别：
		- 进程拥有独立的资源映射表，进程和进程之间的虚拟地址空间（资源映射表）是独立
		- 线程是共享一张资源映射表，共享的是代码段（多个线程相同的函数）、数据段、堆、栈
			- 对于栈，每个任务里，都存放了一个栈顶指针容器，每当任务切换后，CPU的栈指针就被任务里的容器赋值
				- 每个任务都要自己的栈空间，局部变量，不共享 。
				- 硬件上（CPU中）只有一个栈顶寄存器，所以在这个调度体中也只会有一个栈顶指针。
					- 在任务切换时，CPU 的栈顶寄存器（如 x86 的 `RSP` 或 ARM 的 `SP`）会被重新赋值为当前处于运行态线程的栈顶地址。

- 2MLS解决方法
	- 问题发送原因
		- 服务器监听描述符，绑定一个固定端口，一旦服务器处于TIME_WAIT状态，等待2MLS(发的时间 + 收的时间)，才能退出该状态。默认在保持这个状态是，当前的端口，继续占用中，服务器如果重启，这个端口就被占用，导致重启后bind失败，等待2分钟左右才能恢复。
	- 解决方法
		- 配置系统这个socket在TIME_WAIT,不在占用该端口，保持最后一次挥手的缓存，保证可以重传
		- `setsockopt / getsockopt`
	- 服务器启动后，客户端和服务器连接，服务器关闭，第二次启动会导致端口占用

- epoll与select**区别面试常问**
  - 底层数据结构不同，epoll的底层是采用红黑树 + 双向链表；select底层采用位域技术
  - 底层的数据处理效率不同，一旦集合里发生的事件，epoll采用logN复杂度查找，而select采用N复杂度查找
  - 应用层，select返回的是发生改变的位域，仍然需要用户层遍历查找究竟是哪些IO。而epoll直接从双向链表中取得以发生的事件集，只需要遍历这个返回的事件集，就可以得到每个发生反应IO了
  - epoll牺牲了空间，适合IO很多，但发生事件的频率不高的场景，如：环境采集、网页服务
  - select牺牲了时间，适合IO很多，但发生事件频率极高的场景，如：网游
  - epoll支持ET模式和LT模式
- epoll触发模型 ET（边沿触发）和LT（水平触发）
  - 1 + x 中 x 客户端发来消息，暂时到内核传输层 recv搬移到用户空间，导致 一次性是接收不完，需要重复接收，但循环recv导致不知道什么时候退出。 返回值 = 0才退出不可以取（这种方式需要对方退出，但不避免对方占用不使用）
  - epoll_wait默认触发条件是有数据就触发（水平触发）
  	- 会导致频繁触发recv（系统调用），导致资源开销大，也可能阻塞导致其他无法进行通信
  	- 只有数据没有处理，就继续
  - 从无到有（边沿触发），EPOLLET
  	- 会导致数据有可能无法处理完，导致数据丢失
  	- 不会出现阻塞其他通信的情况，调用频率低
  - ET模式，需要设置成非阻塞方式
  - select触发条件是有数据
