​	SQL优化，主要就是在优化索引。索引（index）：相当于目录，是帮助MySQL高效获取数据的**数据结构**（树，如：B树、哈希树）

​		索引的弊端：

​			1、索引本身很大，可以存放在内存/硬盘中（一般为硬盘）

​			2、索引不是所有情况均适用，如：a. 少量数据；b. 需要频繁更新的字段；c. 很少使用的字段

​			3、索引会降低增删改的效率（一次增删改，需要同时修改数据文件和索引文件）

​		索引的优势：

​			1、提高查询效率（降低IO的使用率）

​			2、降低CPU使用率（数据有序，因为是B树结构本身有序）

​	索引：通过`INDEX`创建，主键也是一种索引

​	索引分类

​		单值索引：单列字段，一张表中可以多个字段都是设置成单值索引。

​			`create index 索引名 on 表(字段);`

​			`alter table 表 add index 索引名(字段);`

​		唯一索引：该字段的值不能重复。

​			`create unique index 索引名 on 表(字段);`

​			`alter table 表 add unique index 索引名(字段);`

​		主键索引：也是一种唯一索引，只是该索引**不能为NULL**。

​			`CREATE TABLE 表(字段 INT AUTO_INCREMENT PRIMARY KEY, 其他字段的声明...);`

​			`CREATE TABLE 表(字段1 INT NOT NULL, 字段2 INT NOT NULL, PRIMARY KEY (字段1, 字段2));` 复合主键，多个字段组成一个主键

​			`ALTER TABLE 表名 ADD PRIMARY KEY (主键字段名);`

​		复合索引：多个列构成的索引（相当于多级目录，需要满足最左前缀原则。）

​			`create index 索引名 on 表(字段1, 字段2, 字段3...);`  字段1满足后，才能查询后续的字段2、3

​			`alter table 表 add index 索引名(字段1, 字段2, 字段3...);`



​		删除索引：`drop index 索引名 on 表;`

​		查询索引：`select index from 表;`

返回结果的表的意思

| **字段名**        | **核心含义**            | **说明与关注重点**                                           |
| ----------------- | ----------------------- | ------------------------------------------------------------ |
| **id**            | 查询的执行顺序标识      | `id` 值越大优先执行；`id` 相同则从上到下顺序执行。           |
| **select_type**   | 查询的类型              | 区分普通查询、联合查询（`UNION`）、子查询等。                |
| **table**         | 当前正在处理的表        | 显示这一行数据来自于哪张表（或临时表）。                     |
| **type**（核心）  | **访问类型 / 查找方式** | **判断性能的关键**！从最好到最差依次为： `system` > `const` > `eq_ref` > `ref` > `range` > `index` > `ALL` |
| **possible_keys** | 可能用到的索引          | 优化器预测可能会用到的索引列表（不一定真的使用）。           |
| **key**（核心）   | **实际使用的索引**      | 数据库最终决定使用的索引名称。如果为 `NULL`，说明没用到索引。 |
| **key_len**       | 使用到的索引字节长度    | 在联合索引中，可以通过该值判断具体用到了索引的前几列。       |
| **ref**           | 索引比较的列或常量      | 显示哪些列或常量被用于与 `key` 中的索引进行比较。            |
| **rows**（核心）  | 预估扫描的行数          | 优化器估算找到目标数据需要扫描的行数，**数值越小越好**。     |
| **filtered**      | 过滤百分比              | 经过表条件过滤后，剩余数据占扫描行数的百分比（按 100% 计算）。 |
| **Extra**（核心） | 额外的补充信息          | 包含非常关键的性能信号（如是否用了覆盖索引、是否发生了排序等）。 |

- `id`: id相同时，从上往下 顺序执行；id不同时，id越大越优先，id为NULL，最后执行
- `select_type`:
  - `PRIMARY`: 包含子查询SQL中的主查询（最外层）
  - `SUBQUERY`：包含子查询SQL中的 子查询（非最外层）
  - `SIMPLE`: 简单查询（不包含子查询、union）
  - `DERIVED`：衍生查询（使用了临时表,查表的结果在做为表进行查询）
  	- 在`from`子查询中只有一张表，该子查询就是`DERIVED`
  	- 早`from`子查询中，如果有`表1 union 表2`，则表1是`DERIVED`，表2就是`UNION`
  - `UNION` ：上面的例子
  - `UNION RESULT`: 告知开发人员，哪些表之间存在union查询
- `type`: 索引类型
  - 常用（按性能由高到低排列）:  `system` > `const` > `eq_ref` > `ref` > `range` > `index` > `all` 
  - 其中，`system`、`const`只是理想情况，实际能达到的程度`ref`、`range`
  - 要对`type`进行优化的前提：有索引
  - `system`: 只有一条数据的系统表 或者 衍生表只有一条数据的主查询。
  - `const`: 仅仅能查到一条数据的SQL，用于`Primary key`（主键） 或者 `unique`（唯一）索引。（`copnst`与索引类型主键索引和唯一索引强相关）
  - `eq_ref`: 唯一性索引，对于每个索引键的查询，返回匹配唯一行数据（原表中的数据有且只有1个，结果表的结果不能多、不能少，即索引表中数据全部查到）【常见于唯一索引 和 主键索引】
  	- 结果表与原表的数据 一 一对应。如果不能一 一对应只能是`ref`级别
  - `ref`: 非唯一性索引，对于每个索引键的查询，返回匹配的所有行（结果表可以是0或者多条，即结果表与原表的数据可以不一样） 
  - `range`: 检索指定范围的行，where后面是一个范围查询（SQL关键字：between , in, > , < , >= , <=）
  	- in 有时候会失效，从而转为 无所有ALL
  - `index`: 查询全部索引数据（查询索引文件，前提有索引），只需要扫描索引表，即不需要所有表中的所有数据
  - `all`: 查询全部表数据 （查询数据文件，包含数据的表），需要全表扫描，即需要所有表中的所有数据
  - 总结
  	- `system / const`：结果只有一条数据
  	- `eq_ref`: 结果多条，但是每条数据是唯一的
  	- `ref`: 结果多条，但是每条数据是0条或者多条
- `possible_keys`: 可能用到的索引，是一种预测，不准确
- `key`: 实际使用到的索引。如果`possible_keys / key`为NULL，则为没有索引。
- `key_len`: 索引的长度。用于判断复合索引是否被完全使用。（需要关注当前数据一个字符占多少个字节）
  - 如果索引字段可以为NULL，MySQL则会使用1个字节用于标识
  - MySQL用2个字节标识可变长度
- `ref`：指明当前表所参照的字段（即筛选条件，如：=右边的值，如果是常量，即ref=为const）【前提是该字段是索引】。与typr中的ref值有不同。
- `rows`:被索引优化查询的数据个数（实际通过索引而查询到的数据个数）
- `Extra`: 
	- `using filesort`: 性能消耗大；需要“额外”的一次排序（查询）
	  - 排序之前，先查询。一般出现在`order by ` 排序关键字中
	  - 对于单索引，如果排序和查找是同一个字段，则不会出现using filesort；如果排序和查询不是一个字段，则会出现using filesort。避免：where哪些字段，就order by哪些字段
	  - 对于复合索引：不能跨列（最左前缀原则）。避免：where和order by按照复合索引的**顺序使用**，不要跨列或无序使用
	  - 有两种算法：双路排序（需要消耗IO次数多）、单路排序
	  	- 双路排序：先从数据表中读取 **“排序字段 + 主键 ID”** 放到内存（`sort_buffer`）中进行排序，排序完成后，再拿着排好序的主键 ID **二次回表**读取查询所需的全部列。
	  		- 极度消耗磁盘 I/O
	  		- 当查询所需返回的所有字段总长度超过了参数 `max_length_for_sort_data` 时，MySQL 优化器为了防止内存溢出，会自动降级使用双路排序。
	  	- 单路排序：一次性把 `WHERE` 过滤后需要的 **“排序字段 + 查询所需的全部列”** 统统加载进内存（`sort_buffer`），直接在内存里排完序后输出结果，避免了二次回表。
	  		- 极度占用内存；容易触发磁盘临时文件排序
	- `using temporary`:性能消耗大，已经有表了，但是不适合（现有的中间数据结构无法直接满足后续步骤（如分组、去重、排序）的要求），必须用到临时表。一般出现在`GROUP BY`语句中。避免：查询哪些列，就根据那些列进行分组`GROUP BY`
	  - 解析过程：
	  - from > on > join > where > group by > having > select dinstinct > order by > limit
	- `using index`: 性能提升。也叫索引覆盖、覆盖索引。出现原因：不读取原文件，只从索引文件中获取数据，即不需要回表查询。
		- 查询条件只有索引字段且显示也只有索引字段（只要使用到的列全部都在索引中，就是索引覆盖）。
		- 如果用到了索引覆盖`using index`时，会对应`possible_keys`和`key`造成影响：
			- 如果没有`where`,则索引只会出现在`key`中
			- 如果有`where`,则索引会出现在`key`和`possible_keys`中
	- `using where`：需要回表查询。在查询语句中，出现必须回原表（总表）查该字段数据，会出现`using where`。
	- `impossible where`：`where` 子句永远为false（该条件组合永远不可能出现）
	- `using join buffer`：性能差，MySQL引擎使用了连接缓存优化。

单表优化：

1、索引一旦进行 升级优化，需要将之前废弃的索引删除，防止干扰。

2、优化1：根据SQL实际解析顺序，调整索引的顺序（即根据from、where等关键子在SQL中实际解析顺序，调整其后面的条件字段，在索引中的位置）

3、优化2：因为范围查询in有时会失效，因此交换索引的顺序，将in后面的字段置后。

4、总结：

​	a、索引不能跨列使用（最左前缀原则），保持索引的定义和使用一样的顺序

​	b、索引需要逐步优化

​	c、将含in的范围查询，放到where条件的之后，防止失效



多表的SQL优化

1、**小表驱动大表** —— 将数据小的循环放在外层，将数据大的循环放在内层。

​	a. 小表：条件字段过滤之后的结果集大小（如：表 A 有 100 万行，但 `WHERE` 条件过滤后只剩 10 行；表 B 有 1 万行，但没有过滤条件。那么 表 A 才是真正的“小表”）

​	b.  对于 `INNER JOIN`（内连接），**优化器会自动分析并选择**结果集较小的那张表作为驱动表，**无论你把小表写在左边还是右边**。

​	c. 对于 `LEFT JOIN`（左外连接），默认强制左表为驱动表、右表为被驱动表（除非优化器通过等价重写转换为了内连接）。因此，**只有使用 `LEFT JOIN` 时，才需要手动把小表放在左边**。

2、索引建立在经常使用的字段上，经常需要增删改的字段建议不要添加索引。[**一般是给大表[被驱动表]添加索引**]

​	a. **`LEFT JOIN`（左连接）**：驱动表是左表，**索引必须给右表（被驱动表）加**。这样在拿左表数据去右表查找时，才能走索引快速定位。如果右表没索引，右表就会被全表扫描（或者使用 Block Nested-Loop / Hash Join），性能极差。

​	b. **`RIGHT JOIN`（右连接）**：驱动表是右表，**索引必须给左表（被驱动表）加**。



避免索引失效的一些原则：

​	1、复合索引，不要跨列或无序使用（最左前缀原则）

​	2、复合索引，尽量使用全索引匹配

​	3、不要在索引上进行任何操作（计算、函数、类型转化），否则索引失效

​	4、复合索引中使用范围查询时，**范围字段自身可以正常走索引（用以定位扫描边界），但会导致其右侧的所有索引字段无法走索引检索（等待结果集有可能导致后面的索引字段数据是无序的）。** —— 尽量把用于范围查询的字段放在复合索引的最后面

​	5、不等于（`!=`）操作**无法利用索引的树形结构进行快速定位**，通常会导致当前字段及其右侧字段的索引失效（极易退化为全表扫描）。—— 可以将 `!=` 改写为 **`IN`** 或 **`UNION ALL`**

​	6、**`IS NULL` 可以正常使用索引**（MySQL 的 B+ 树将 `NULL` 值统一存放在最左侧叶子节点）。**`IS NOT NULL` 通常无法走索引**，因为大部分数据都满足“不为空”，优化器计算成本后会直接选择全表扫描。 —— 建表时尽量给列加上 **`NOT NULL` 约束** 并设置**默认值**（如 `DEFAULT ''` 或 `DEFAULT 0`），用明确的默认值等值查询（如 `status = 0`）来替代 `IS NOT NULL` / `IS NULL`。

​	7、 在索引列上进行**计算、函数调用或隐式类型转换**（如字符串不加单引号），会导致该字段及其右侧的所有索引彻底失效。 —— 将计算或转换拿到 SQL 之外（代码层）处理，确保传给数据库的是字段原生的纯等值/范围参数。

​	8、尽量使用索引覆盖`using index`

​	9、`like`尽量以“常量”开头，不要以"%"开头，否则索引会失效。 —— 引入专业的搜索引擎，如MySQL的FULLTEXT全文索引  或者 使用索引覆盖

​	10、尽量不要在索引上使用类型转换（无论显示还是隐式），否则索引会失效

​	11、`OR` 条件两边看：两边都有独立索引，能走 Index Merge；一边没索引，全表扫描没得跑（索引失效）

​	12、**传统原理**：`IN` 适合子查询结果集小的场景；`EXISTS` 适合外层主表小、子查询表大的场景（以小表驱动大表）。

​		**现代版本（5.7/8.0+）**：优化器会自动改写 `IN` 为 Semi-Join，两者性能基本一致。

​		**避坑铁律**：做**否定查询**时，**严禁使用 `NOT IN`**（有 `NULL` 污染风险），统一改用 **`NOT EXISTS`** 或 **`LEFT JOIN ... WHERE 右表.id IS NULL`**。

​	13、order by优化：

​		a. 选择使用单路 或者 双路；调整buffer的容量大小

​		b. 避免select *

​		c. 复合索引 不要跨列使用

​		d. 保证使用索引和定义的索引的顺序一致性



所有SQL优化的核心：

- **减少数据传输量（减少 IO）** —— 让数据库只找需要的数据。
- **减少计算复杂度（节省 CPU/内存）** —— 避免在数据库层面做大量的排序、函数计算和类型转换。



SQL优化一般是针对一类查询进行优化，之后查询条件改变，需要对索引进行变化或者更改。（SQL优化本质：按模式优化 和 索引是动态演进的）

SQL排查 —— 慢查询日志

​	是一种MySQL提供的一种日志记录，用于记录MySQL中响应时间超过阈值的SQL语句

​	慢查询日志默认关闭，建议：在开发调用时打开，而发布是关闭

```mysql
-- 查看
-- 查看慢查询日志是否开启，以及日志保存路径
SHOW VARIABLES LIKE 'slow_query_log%';

-- 查看判定为慢查询的时间阈值（单位：秒，默认 10 秒）
SHOW VARIABLES LIKE 'long_query_time';

-- 查看是否记录没有使用索引的 SQL
SHOW VARIABLES LIKE 'log_queries_not_using_indexes';

-- 查看日志输出形式（FILE 文本文件 / TABLE 数据库表 / NONE）
SHOW VARIABLES LIKE 'log_output';

-- 临时开启
-- 开启慢查询日志（1 为开启，0 为关闭）
SET GLOBAL slow_query_log = 1;

-- 设置慢查询阈值为 1 秒（执行超过 1 秒即被记录）
-- 注意：设置后需要重新打开一个新的会话/连接才能看到 long_query_time 的变化
SET GLOBAL long_query_time = 1;

-- 开启记录没有使用索引的 SQL（可选）
SET GLOBAL log_queries_not_using_indexes = 1;

-- 设置日志输出到文本文件（默认）或表
SET GLOBAL log_output = 'FILE';

-- 永久开启
-- 配置文件的[mysqld]节点下添加配置
[mysqld]
# 开启慢查询日志
slow_query_log = 1

# 指定慢查询日志文件存放路径
slow_query_log_file = /var/lib/mysql/mysql-slow.log

# 设定执行时间超过 1 秒的 SQL 记录到慢查询日志
long_query_time = 1

# 记录没有使用索引的 SQL（可选）
log_queries_not_using_indexes = 1

# 限制每分钟记录未走索引 SQL 的最大数量（防止日志文件过大，可选）
log_throttle_queries_not_using_indexes = 10

-- 刷新
-- 查看当前系统累计记录了多少条慢查询
SHOW GLOBAL STATUS LIKE 'Slow_queries';

-- 重新加载/刷新日志文件（通常用于切割或清除慢日志后重新生成）
FLUSH LOGS;


```

**锁机制**：解决因资源共享而造成的并发问题。

- 分类：
	- 操作类型：
		- 读锁（共享锁）：对同一个数据，多个读操作可以同时进行。
		- 写锁（互斥锁）：对同一个数据，当前正常写的操作没有完成，其他对改数据的写入都无法进行。
	- 操作范围：
		- 表锁：一次性对一张表整体加锁。如：MyISAM存储引擎使用表锁，开销小、加锁快；无死锁；但锁范围大，容易发生锁冲突、并发性低。
			- **为什么传统表锁容易导致“读操作失败”或“读不到数据”？**
				1. **读写互斥（锁冲突）**： 当写操作给数据 A 所在整张表加上**排他锁（表锁）\**时，读操作会被挡在外面\**强行排队**。如果写操作耗时稍长，读操作等不及超时了，就会直接报错（如 `Database is locked`）。
				2. **数据中间态（脏读/查空）**： 如果写操作还没提交（比如正在把数据 A 删除或修改），而读操作强行去读，就会遇到尴尬的**数据不一致**：索引里可能还残存着数据 A 的信息，但引擎真正去找数据时却发现“已经被清空了”。
			- **现代数据库如何破解？**
				- **开启 MVCC（MySQL） / WAL （SQLite）模式**：写数据时保留一份“旧快照”，读操作直接去读旧快照。这样**写不阻塞读、读不阻塞写**，既不卡顿报错，也不会读到改了一半的脏数据。
		- 行锁：一次性对一条数据加锁。如：InnoDB存储引擎使用行锁，开销大，加锁慢；容易出现死锁，不易发生锁冲突、并发高（很小概率发生高并发问题：脏读、幻读、不可重复读）
			- 脏读、不可重复读、幻读，根本原因不是“行锁”引起的，而是“事务隔离级别（Isolation Level）”设置不当导致的
		- 页锁



一般**写操作占比 $\ge 10\%$ 或存在并发写** $\rightarrow$ **强制选择 InnoDB**。**纯读（读占比 $> 90\%$）且无写并发** $\rightarrow$ 在早期版本中 MyISAM 因为结构简单略有优势，但在 **MySQL 5.7/8.0 中，InnoDB 的 Buffer Pool 缓存优化后读性能已完全不输 MyISAM**。

**事务支持（ACID）**：只要业务需要 `BEGIN / COMMIT / ROLLBACK` $\rightarrow$ **100% 选 InnoDB**（MyISAM 完全不支持事务）。

**崩溃恢复（Crash Safety）**：需要断电/异常宕机后数据自动修复 $\rightarrow$ **100% 选 InnoDB**（依赖 Redo Log 双写保障；MyISAM 断电极易损坏 `.MYI` 索引文件）。

**外键与行锁**：需要外键约束或行级排他锁 $\rightarrow$ **100% 选 InnoDB**。



行锁的注意事项：

1、如果没有索引，则行锁会转为表锁。

2、行锁的一种特殊情况：间隙锁 —— 值在范围内，但却不存在。MySQL会自动给间隙加锁  —— 临键锁

​	a. **间隙锁（Gap Lock）**：锁住的是两个索引记录之间的**开区间**（不包含两端的数据行），目的是防止其他事务在这个区间内插入新数据，从而彻底**解决“幻读（Phantom Read）”问题**。

​	b.在 InnoDB 的可重复读（RR）隔离级别下，真正的行锁其实是 **临键锁（Next-Key Lock）** = **记录锁（Record Lock，锁具体行） + 间隙锁（Gap Lock，锁两边间隙）**。

3、行锁：如果有where，则实际加锁的范围，取决于“WHERE 后的条件”以及“使用的是什么索引（主键/唯一索引 vs 非唯一索引）”。

​	a. 主键/唯一索引等值命中 $\rightarrow$ 仅锁**单行**（记录锁）。

​	b. 查不存在的值 / 非唯一索引 / 范围查询 $\rightarrow$ 锁**行 + 间隙区间**（临键锁/间隙锁）。



如果是查询数据，能否加锁？可以，添加关键字：`for update`

DDL与DML

| **特性**                 | **DDL (数据定义语言)**                | **DML (数据操作语言)**                      |
| ------------------------ | ------------------------------------- | ------------------------------------------- |
| **主要对象**             | **结构**（表、索引、视图）            | **数据**（行、记录）                        |
| **典型命令**             | `CREATE`, `ALTER`, `DROP`, `TRUNCATE` | `INSERT`, `UPDATE`, `DELETE`                |
| **事务与提交**           | **隐式自动提交（Auto-commit）**       | **需要手动 `COMMIT`**（除非开启了自动提交） |
| **能否回滚（ROLLBACK）** | **通常无法回滚**                      | **可以回滚**                                |

**DDL（Data Definition Language，数据定义语言。操作表结构）：** 动的是“骨架”，**自动提交，不能回滚**。

**DML（Data Manipulation Language，数据操作语言。操作表数据）：** 动的是“内容”，**需要 `COMMIT` 才会生效，支持回滚**。	

为什么 DDL 不需要 `COMMIT`，而 DML 需要？

1. **DDL 会触发“隐式提交”（Implicit Commit）：** 当你在数据库中执行一条 DDL 语句（如 `CREATE TABLE` 或 `ALTER TABLE`）时，数据库会在执行前**自动提交**当前事务中未提交的 DML 操作，并在 DDL 执行完后**再次自动提交**。因此，**DDL 无需也无法手动 `COMMIT`**，一旦执行立刻生效。
2. **DML 处于“事务（Transaction）”保护中：** 当你执行 `INSERT`、`UPDATE` 或 `DELETE` 时，修改暂时保存在事务缓冲区/日志中，其他客户端暂时看不到或者不能确信该修改已永久生效。只有当你明确执行 **`COMMIT;`** 时，这些修改才会真正永久写入数据库；如果发现操作有误，可以执行 **`ROLLBACK;`** 来撤销修改。

**TCL（Transaction Control Language，事务控制语言）：** 包括 `COMMIT`（提交）、`ROLLBACK`（回滚）、`SAVEPOINT`（保存点）。

**DCL（Data Control Language，数据控制语言）：** 包括 `GRANT`（授权）、`REVOKE`（撤销权限）。



索引 是帮助MySQL高效获取数据的**排好序**的数据结构

数据库底层数据结构优化，MySQL的底层数据结构为B+树

存储引擎用来形容数据库表的。如：MySQL的存储引擎InnoDB。



MyISAM是MySQL数据库5.5版本之前的默认存储引擎【设计理念：性能优先，不可靠，处理更多单线程的读取数据，使用表锁】

MyISAM的数据表由三个文件组成：

- **.frm**：表结构文件
- **.MYD**：数据文件
- **.MYI**：索引文件
	它支持**B-tree索引**和**全文索引**，索引与数据分离（非聚簇索引），通过索引指向实际数据地址，从而加快查询速度。此外，MyISAM还提供**键缓存（Key Cache）**机制，将索引块加载到内存中，进一步提升读取效率

MyISAM索引和数据文件是分离的（非聚集索引）

InnoDB是MySQL数据库5.5版本开始的默认存储引擎（5.5及以后版本）【设计理念：事务优先，数据可靠，防止高并发问题，使用行锁】

 InnoDB的数据表通常由两个文件组成（独立表空间模式下）： 

- frm：表结构文件（MySQL 8.0后统一整合至系统数据字典中，不再单独独立） 
- ibd：数据与索引文件（表空间文件）
	- 它采用聚簇索引（Clustered Index）架构，将主键索引与数据记录紧密紧挨存储在一起，叶子节点直接包含完整的行数据。辅助索引（二级索引）则记录主键值，查询时通过主键二次查找（回表）获取真实数据。此外，InnoDB还提供缓冲池（Buffer Pool）机制，将数据页和索引页同时缓存至内存中，大幅提升读写效率 

InnoDB索引和数据文件是存放在一起的 —— **聚簇索引（Primary Key）**

![](../../img/new_208_sql%E4%BC%98%E5%8C%96.png)

**左图：聚簇索引（Primary Key）** （也叫聚集索引）

- **作用**：按主键（如数字 ID 15, 18, 20...）组织的 B+ 树。
- **特征**：它的**叶子节点直接存放了整行完整数据**（如数字 ID 下方对应的姓名和其它字段）。表中真实的数据行只在这棵树里保存一份。

**右图：二级索引 / 辅助索引（Secondary Key）**

- **作用**：按非主键字段（如姓名 Alice, Bob, Eric...）建立的 B+ 树，用于加速非主键查询。
- **特征**：它的**叶子节点不存完整数据，而是存储“索引字段 + 主键值”**（如 `Alice -> 18`，`Bob -> 15`）。

**为什么要这样设计？**

1. **避免数据冗余**：如果每个二级索引（比如给年龄、性别、姓名分别建索引）都把整行完整数据复制一遍，会极大浪费磁盘空间。
2. **实现“回表”查询**：当你执行 `SELECT * FROM table WHERE name = 'Alice'` 时，数据库会先查右边的**二级索引树**找到 `Alice` 对应的主键 ID 是 `18`；然后再拿着 ID `18` 去查左边的**主键树**取回整行完整数据（这个过程称为**回表**）。

**为什么建议InnoDB表必须建主键，并且推荐使用整型和自增主键**

1. 使用主键
	1. **避免引擎盲目选择/创建隐式主键**：
		- 如果显式定了主键，InnoDB 直接用主键构建聚簇索引。
		- 如果没有定主键，InnoDB 会寻找第一个不为 NULL 的唯一索引（Unique Key）作为聚簇索引。
		- 如果连唯一索引都没有，InnoDB 会自动在后台生成一个 6 字节的隐式自增列（`row_id`）作为聚簇索引。
	2. **避免系统开销**：
		- 所有没有主键的表会共享同一个全局的 `row_id` 计数器，并发写入时竞争激烈，容易出现性能瓶颈。因此，显式指定主键可以节省资源并保证高效性能。
2. 整型
	1. **占用空间小，提高缓存命中率**：
		- 整型（如 `INT` 占 4 字节，`BIGINT` 占 8 字节）比字符串（如 36 字节的 UUID）小得多。
		- **节省二级索引空间**：InnoDB 的所有二级索引叶子节点都会存储主键值。主键越小，每个二级索引页能容纳的索引项就越多，能大幅减少磁盘 I/O 并提高 Buffer Pool 的内存利用率。
	2. **数值比较和计算极快**：
		- B+ 树在查找、插入和节点分裂时，需要频繁进行键值的**比较**。
		- 整型比较是 CPU 的原生硬件操作，效率极高；而字符串比较需要逐字符对比，还要考虑字符集和校对规则（Collation），开销明显更大。
3. 自增主键
	1. **有序插入，避免页分裂（Page Split）与数据碎片**：
		- **自增主键**：每次插入的新记录都会追加到 B+ 树的末尾（最右侧叶子节点）。数据页按顺序填满，磁盘写满后直接开辟新页，**磁盘写入效率最高（顺序 I/O）**。
		- **非自增/随机主键（如 UUID）**：新插入的数据主键值是随机的，往往需要插入到 B+ 树中间的某个已满数据页中。这会导致存储引擎将原数据页拆分为两个新页（**页分裂**），带来大量随机磁盘 I/O、内存数据页移动以及大量的页碎片。
	2. **聚集索引结构聚拢性高**：
		- 自增主键使得物理存储更加紧凑，几乎没有数据空隙，进一步提升了查询和扫表（Table Scan）的效率。



聚集索引（Clustered Index）与非聚集索引（Non-Clustered Index）最核心的区别在于：**索引的逻辑顺序与数据的物理存储顺序是否一致，以及索引的叶子节点中到底存了什么。**

| **对比维度**         | **聚集索引（Clustered Index）**                      | **非聚集索引（Non-Clustered Index / 辅助索引）**             |
| -------------------- | ---------------------------------------------------- | ------------------------------------------------------------ |
| **存储物理位置**     | 索引与数据**存放在一起**，数据按主键顺序紧密排列     | 索引与数据**分离**，单独维护一棵索引树                       |
| **叶子节点内容**     | 存储**整行完整数据**                                 | 存储**索引字段 + 主键值**（或数据物理地址指针）              |
| **一张表中的数量**   | **只能有 1 个**（因为物理数据行只能按一种顺序排列）  | 可以有 **多个**（根据业务需求建立多个辅助索引）              |
| **查询过程**         | 一次查找，定位到叶子节点即可直接拿到数据             | 查到叶子节点获取主键值后，通常需要**“回表”**去聚集索引树查完整数据 |
| **写性能（增删改）** | 成本较高（插入新行可能导致页分裂与数据物理位置重排） | 成本相对较低（主要修改索引树，不影响真实数据的物理存储）     |



**B+ 树相比 B 树的优势（为什么数据库常用 B+ 树？）**

1. **更少的磁盘 I/O（树更矮胖）** 由于数据库的节点通常对应一个磁盘页（如 16KB），B+ 树的非叶子节点只保存索引 Key，不存整行数据，因此一个节点能容纳上千个 Key。树的高度通常控制在 3-4 层内，查找任意数据只需 3-4 次磁盘 I/O。
2. **范围查询效率极高** 数据库中极常出现 `WHERE age BETWEEN 18 AND 30` 或 `ORDER BY id` 这类查询。B+ 树只需在树中找到 `18` 所在的叶子节点，然后顺着叶子节点的**双向链表**一直往后读取，直到遇到 `30` 即可，完全不需要在树的上下层之间频繁回溯。
3. **查询性能更加稳定** B+ 树的所有数据都在叶子节点，因此每一次查询的 I/O 次数都是相同的（即树的高度），性能表现非常平稳。



联合索引：把多个字段组合起来建立的“多级排序”索引。只有包含最左边的字段，数据库才能沿着树的排序逻辑快速定位；如果跳过了左边的字段，右边的字段在树里就是无序的，索引就会失效。（按字段左到右，对B+树进行排序，当前字段相同，在比较下一个字段）

```mysql
-- 创建新表时添加
CREATE TABLE users (
    id INT AUTO_INCREMENT PRIMARY KEY,
    last_name VARCHAR(50),
    first_name VARCHAR(50),
    age INT,
    -- 建立 (last_name, first_name, age) 的联合索引
    INDEX idx_name_age (last_name, first_name, age)
);

-- 旧表中添加
ALTER TABLE users 
ADD INDEX idx_name_age (last_name, first_name, age);
```

**列的顺序极度重要（索引最左前缀原则）**：根据最左前缀匹配原则，放在**最左边**的列必须是查询中最常用、区分度最高（重复值最少）的列。例如 `(last_name, first_name)` 和 `(first_name, last_name)` 是完全不同的两个索引。

- 原则本身： **只有查询条件从最左边的列开始，索引才能被有效利用**。
- 范围查询会"断层"：**等值查询（=、in）不会断，范围查询（>、<、between、like前缀）后面的列全部失效**
-  顺序无关性（优化器会自动调整）：MySQL 查询优化器会自动调整 WHERE 条件顺序去匹配索引列顺序，**不用手动把 SQL 里的字段顺序写得和索引一致**。
- 索引下推（Index Condition Pushdown, ICP）：ICP 让联合索引里"断层"之后的列，也能在索引层面帮忙过滤，减少回表，但不能改变排序和范围定位的本质。
- 联合索引与排序（避免 filesort）

==联合索引的本质，是把多个列**按顺序拼接排序**后存进同一棵 B+ 树； 用好它的关键在于**让查询条件符合"最左前缀 + 等值在前、范围在后"的排序逻辑**， 并尽量设计成**覆盖索引**来省掉回表这一步。==

**联合唯一索引**：如果希望多个字段的组合值是唯一的（例如“每个部门里的员工编号不能重复”），可以使用 `UNIQUE` 关键字：

```mysql
ALTER TABLE employees 
ADD UNIQUE INDEX uk_dept_emp (dept_id, emp_number);
```

**查看已建立的索引**：`SHOW INDEX FROM users;`

| 原则                                   | 说明                                                         |
| -------------------------------------- | ------------------------------------------------------------ |
| **区分度高的列放前面**                 | 区分度越高，一次过滤掉的数据越多（但需结合最左前缀实际查询场景） |
| **等值查询列放前面，范围查询列放后面** | 避免范围列过早出现导致后面的列排序失效                       |
| **尽量让索引覆盖常用查询**             | 减少回表，提高查询效率                                       |
| **避免冗余索引**                       | 如已有 `(a,b,c)`，无需再建 `(a)`、`(a,b)`，前者已包含        |
| **控制索引列数量**                     | 一般不超过 5 个字段，字段太多索引本身也变得臃肿、维护成本高  |
